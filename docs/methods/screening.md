# Screening — how to run it

## What this module is, and what it is not

**It is infrastructure for recording screening. It is not screening.**

The module generates a worksheet from the deduplicated reports, checks that whatever the reviewer
records is internally consistent and complete, and computes the PRISMA flow from what has actually
been decided. Every decision is the human reviewer's (D010), and an automated suggestion cannot
satisfy a `decision` field.

A suggestion set **does** exist. The 194 title/abstract decisions now in the worksheet were entered
by adopting suggestions generated by automated tooling from the titles and abstracts; that set is
kept as an audit artefact at `data/screening/ta_suggestions_2026-11-01.csv`. The worksheet records
which act produced each decision, so the distinction lives in the data and not only in a commit
message. See **Suggestion versus adjudication** below — that section, not this one, is where the
current state is stated.

So "the screening module works" and "the screening is done" are different claims. The current
state of the second is in `results/validation/prisma_counts.md`, which states it in a banner at the
top of the file.

## Where the files live, and why

| Path | Tracked in Git? | Why |
|---|---|---|
| `data/screening/screening_ta.csv` | **yes** | Screening decisions are human research work and cannot be regenerated from anything. They must be version-controlled |
| `data/screening/screening_ft.csv` | **yes** | same |
| `data/screening/ta_suggestions_2026-11-01.csv` | **yes** | What the tooling proposed, kept so that any adopted decision can be audited against its source. Holds no `decision`, `reviewer`, `screened_date` or approval column |
| `data/screening/verification_sample.csv` | **yes** | The blinded verification instrument. Protected: not regenerated or edited once drawn |
| `data/processed/**` | no — gitignored | Regenerable from the raw export by re-running the pipeline |

This is why the worksheets are **not** under `data/processed/`: that directory is ignored as
regenerable, and putting irreplaceable decisions there would mean losing them on any fresh clone.

## 1. Generate the worksheet

```bash
.venv/Scripts/python -m scripts.screening.worksheet --stage ta
```

One row per **unique report** (`report_id`), taken from `data/processed/dedup/report_index.csv`,
so duplicates are already collapsed. The raw export's checksum and the raw-to-derived consistency
of the parsed data are verified first; if either fails, no worksheet is written.

Running it again **refuses to overwrite**, because the file may hold your decisions. To pick up
records added by a later search:

```bash
.venv/Scripts/python -m scripts.screening.worksheet --stage ta --refresh
```

`--refresh` merges on `report_id`: every recorded decision is carried across, and only genuinely
new reports are added. If a report that holds a decision has disappeared from the source set, the
command **fails** rather than dropping it — that would discard your work silently.

## 2. Record decisions

Edit only these columns: **`decision`, `decision_basis`, `reason_code`, `reviewer`,
`screened_date`, `adjudicated_date`, `notes`**. The `suggestion` and `suggestion_reason_code`
columns are machine-written and are preserved, never edited. Everything else is derived and is
checked against the source data; an edit there is reported as an error, because it usually means a
spreadsheet re-import has damaged the file.

| Column | Values |
|---|---|
| `decision` | `include` · `exclude` · `unresolved` · empty (not yet screened) |
| `decision_basis` | `adopted_from_suggestion` · `independently_adjudicated`; **required** whenever a decision is recorded |
| `reason_code` | required for `exclude`, forbidden otherwise; from `config/screening.yaml` |
| `reviewer` | required whenever a decision is recorded |
| `screened_date` | required whenever a decision is recorded |
| `adjudicated_date` | **required** when the basis is `independently_adjudicated`; must be empty otherwise |
| `notes` | required when `reason_code` is `other` |
| `suggestion`, `suggestion_reason_code` | machine-written, read-only; what the tooling proposed |

**`unresolved` is a legitimate entry, not a failure.** Use it whenever the abstract does not let
you decide honestly; the record then carries forward to full text. Leaving something unresolved is
always preferable to guessing.

### A spreadsheet caveat

Opening the CSV in Excel is fine, but import it as **UTF-8** and save back as CSV, not as XLSX.
A mis-set import can truncate abstracts, drop rows or reformat PMIDs. The validator detects all
three — it re-checks the row set and the derived columns against the upstream data — but it is
easier to avoid than to repair.

## Suggestion versus adjudication

Two different acts can produce a `decision`, and the worksheet records which one did.

| `decision_basis` | What it asserts |
|---|---|
| `adopted_from_suggestion` | The reviewer accepted an automated suggestion for this record **without judging it individually**. The decision equals the suggestion and the reason code equals the suggested reason code. This is **not** independent adjudication and must not be reported as such |
| `independently_adjudicated` | The reviewer judged the record from its own evidence. A suggestion may or may not exist; where one exists the decision may agree with it or differ from it |

Keeping the suggested verdict but **changing the reason** is an adjudication, not an adoption
(D017): adoption requires that *both* the decision and the reason code match what was suggested.
A decision that differs from its suggestion cannot have been adopted from it.

### What independent adjudication requires

All five, or the row is rejected:

1. `decision` — the verdict itself: `include`, `exclude` or `unresolved`
2. `reviewer` — who judged it
3. `screened_date` — when the record was screened
4. `decision_basis = independently_adjudicated`
5. `adjudicated_date` — when the adjudication was made

The first is a requirement, not an assumption: a `decision_basis` recorded with no `decision` is an
error, so a row cannot claim an adjudication it has no verdict for.

The fifth is deliberately separate from `screened_date`. The 194 existing rows already carry a
reviewer and a screening date from the bulk adoption; without its own date, flipping one field
would convert a provisional record into a formal one with no new evidence and no new date. An
`adjudicated_date` on a row that is **not** `independently_adjudicated` is also an error.

These rules live in one function, `worksheet.adjudication_problems`, which the validator, the
full-text carry-forward and the PRISMA gatherer all call. They therefore cannot disagree about
whether a row is valid, and a row the validator would reject can never promote a report into the
formal flow.

## 3. Validate

```bash
.venv/Scripts/python -m scripts.screening.validate_screening --stage ta
```

Writes `results/validation/screening_ta_validation.md`. Exit 1 on any error.

**Errors:** unknown decision · unknown suggestion · exclusion with no reason · reason not
permitted at this stage · reason recorded on an inclusion · decision with no reviewer · decision
with no `screened_date` · **decision with no `decision_basis`** · unknown `decision_basis` ·
`decision_basis` with no decision · basis `adopted_from_suggestion` with no suggestion recorded ·
basis `adopted_from_suggestion` where the decision differs from the suggestion · basis
`adopted_from_suggestion` where the reason code differs from the suggested one · basis
`independently_adjudicated` with no `adjudicated_date` · `adjudicated_date` on a row that is not
independently adjudicated · `other` without justification · duplicate `report_id` · rows added or
deleted · a derived column edited · a retrieval status used as an exclusion reason.

**Warnings:** reports not yet screened · reports left `unresolved` · decisions adopted from a
suggestion · full text retrieved but not yet screened.

### The `--final` gate

```bash
.venv/Scripts/python -m scripts.screening.validate_screening --stage ta --final
```

`--final` is the assertion "this stage is a result, not work in progress", and it turns two
warnings into errors:

1. **Incompleteness** — any report not yet screened, or left `unresolved`, fails. `unresolved` is a
   legitimate working entry but is not a decision, so it must be settled before the flow is final.
2. **Any row whose basis is `adopted_from_suggestion`** — under D010 a suggestion cannot satisfy a
   decision field, so a stage holding adopted rows is not a screened stage however complete it
   looks.

Run **without** `--final` while screening is in progress; nothing is blocked and both conditions
appear as warnings. Enforcement is forward-only: the gate prevents an unadjudicated stage being
reported as a result, and does not alter the fact that the existing rows were recorded by adoption.
On the current data `--stage ta --final` **fails**, on the 194 adopted rows.

## 4. Full text

```bash
.venv/Scripts/python -m scripts.screening.worksheet --stage ft
.venv/Scripts/python -m scripts.screening.validate_screening --stage ft
```

The full-text worksheet is built from the title/abstract **includes** only. It adds
`full_text_status` (`sought` · `retrieved` · `unavailable`) and `full_text_source`. A report whose
full text is `unavailable` **cannot carry an eligibility decision** — PRISMA reports it as *not
retrieved*, which is not an exclusion, and the validator enforces that.

Full-text decisions carry their own `decision_basis` and `adjudicated_date` under the same rules as
title/abstract (D018). There is **no** `suggestion` column here, because no suggestion mechanism
exists at full text; a full-text basis of `adopted_from_suggestion` would have nothing to refer to.

A further derived column, `source_ta_decision_basis`, records how the *title/abstract* decision that
carried the report forward was made. It is recomputed on every refresh, so adjudicating a source
record promotes its full-text row automatically. It is a convenience copy and **not** the evidence:
the PRISMA attribution looks each report up in the title/abstract worksheet and re-validates that
row, so an edited copy cannot promote anything.

Building the worksheet from includes that were adopted rather than adjudicated would propagate
automated output into the next stage. That **warns** by default and is **refused** under `--final`.
A title/abstract row that fails validation carries no basis forward at all — provenance cannot be
asserted for an invalid row — so its full-text row is attributed as `ft_invalid_source` rather than
inheriting a status it has not earned.

### Stale full-text rows are reported, never silently dropped

A full-text row can go stale: its source record may have been re-decided as an exclusion, may now
fail validation, or may have left the upstream data altogether. None of these causes a deletion.

* `worksheet --stage ft --refresh` **refuses outright** if a row that holds recorded work is no
  longer in the source set, naming the reports. Regenerating would discard the reviewer's work, so
  the command fails and asks for the cause to be investigated first.
* Rows that hold no recorded work are rebuilt from the current include set, and any row that is no
  longer attributable is still **counted and reported** in the PRISMA attribution (below) rather
  than disappearing. The five states always sum to the row count, so nothing can vanish unnoticed.
* The validator independently reports reports missing from the worksheet and reports present in the
  worksheet but absent from the source set, as errors.

## 5. PRISMA counts

```bash
.venv/Scripts/python -m scripts.screening.prisma
```

Writes `results/validation/prisma_counts.md`. Every number is derived from a dataset that exists or
printed as `<pending>`; **nothing is estimated**. `<pending>` means the stage has not been done,
which is deliberately distinguished from a zero — the two are different claims.

### Formal versus provisional accounting (D019)

The report has two separate sections, and a count never appears in both.

* **Formal flow** — counts **independently adjudicated decisions only**. On the current data this
  reads 0 screened, 0 excluded, 0 taken forward. Those zeros are correct: no decision has been
  adjudicated.
* **Provisional screening outcome** — explicitly headed *NOT part of the PRISMA flow*. It reports
  the adopted decisions and their reason counts: 194 provisional decisions, 109 provisionally
  excluded, 85 provisionally taken forward, 0 provisionally unresolved. These are proposals
  awaiting adjudication and must not be reported as flow counts.

A record moves from the provisional section into the formal flow the moment it is independently
adjudicated; its original suggestion stays recorded. A banner at the top of the report states
whether the screening is independently adjudicated, so the distinction cannot be missed by someone
reading only the counts.

### The five full-text attribution states

Every row in the full-text worksheet is assigned exactly one state, decided **per row** by looking
its report up in the title/abstract worksheet and re-validating it — not by subtraction, so each
state says *why* the report is where it is:

| State | Meaning |
|---|---|
| `ft_sought` | The source title/abstract row is valid, is an `include`, and was **independently adjudicated**. This is the only state that counts as formal retrieval |
| `ft_provisional_sought` | Source row is valid and an `include`, but its basis is `adopted_from_suggestion`. Carried from automated output, so not a formal retrieval |
| `ft_invalid_source` | The source row exists but **fails validation**, so no provenance can be asserted for it |
| `ft_ineligible_source` | The source row is valid but is **no longer an `include`** — it was re-decided as an exclusion or left unresolved. A stale row |
| `ft_unattributed` | **No such report** exists in the title/abstract worksheet at all |

On the current data: `ft_sought` 0, `ft_provisional_sought` **85**, `ft_invalid_source` 0,
`ft_ineligible_source` 0, `ft_unattributed` 0.

### Reconciliation identities

Checked on every run; a violation is an error and the run fails, because a flow that does not
reconcile is not a flow:

```
identified − duplicates                                        == unique reports
unique reports                                                 == rows in the TA worksheet
ta_excluded + ta_included + ta_unresolved                       == ta_screened
ta_adjudicated + ta_adopted + ta_invalid + ta_unscreened        == ta_total
prov_excluded + prov_included + prov_unresolved                 == ta_adopted
ta_screened                                                     == ta_adjudicated
ft_sought + ft_provisional_sought + ft_invalid_source
         + ft_ineligible_source + ft_unattributed               == ft_rows
ft_sought                                                       <= ta_included (adjudicated)
ft_provisional_sought                                           <= prov_included
full-text decisions                                             <= assessed
full-text exclusions                                            == sum of reason counts
```

Eleven identities in all. The two sum-to-total ones — `ta_total` and `ft_rows` — are what make
silent loss impossible: every title/abstract row and every full-text row must land in exactly one
bucket, so a record cannot be dropped, double-counted or quietly reclassified without the
arithmetic failing. The first three are the pre-existing PRISMA identities, unchanged.

Included **studies** and studies in synthesis stay `<pending>` regardless of screening progress,
because `study_id` is assigned by the reviewer at full text: several reports can describe one
population (D004), and the pipeline cannot infer that.

## 6. Blinded verification of the recorded decisions

```bash
.venv/Scripts/python -m scripts.screening.verify_sample --draw     # write the blinded sheet
.venv/Scripts/python -m scripts.screening.verify_sample --score    # unblind and report agreement
```

The recorded decisions were entered by adopting a suggestion set. Checking them against the same
tooling that produced them would be circular, so this hands the reviewer a random sample of records
**with the recorded decision withheld** and compares the reviewer's independent judgement
afterwards. Everything is fixed before the draw, so the exercise cannot be made post-hoc:

| | |
|---|---|
| Sample size | **40 of 194** (20.6%), simple random without replacement |
| Seed | the first 8 hex digits of a SHA-256 digest of the sampling frame — nobody chooses it. **Two rules exist**: the existing sample was drawn under `file_bytes_crlf_v1`, later draws use `ordered_report_ids_v1` (D020). See *Which worksheet the seed came from* and *The canonical sampling-frame digest* below |
| Response columns | `your_decision`, `your_reason_code`, `your_notes` — 3 per record, so **120 response cells** |
| Acceptance rule | **ADOPT** at ≥ 95% · **EXTEND** at ≥ 90% and < 95% · **RE-SCREEN** below 90%. Both thresholds are inclusive at their lower bound. See *What each verdict means* below |
| Asymmetry rule | any record the reviewer would *include* that was recorded as *exclude* triggers a sweep of every record excluded under that same reason code, whatever the headline rate. Erroneous exclusion loses evidence irrecoverably; the opposite direction only costs retrieval effort, so it is recorded but triggers nothing |

### How agreement is calculated

**At the record level.** One comparison per sampled record, between the decision recorded in the
worksheet and the reviewer's `your_decision`. The rate is the proportion of exact matches on the
decision value — `include`, `exclude` or `unresolved`.

| Field | Enters the agreement rate? | Treatment |
|---|---|---|
| `your_decision` | **yes** | the only field in the rate |
| `your_reason_code` | **no** | validated against the title/abstract vocabulary, then reported separately as agreement among *concordant exclusions only* |
| `your_notes` | **no** | never scored; free text for the reviewer |

So 40 sampled records yield 40 comparisons, not 120. The sheet has 120 response cells because each
record takes three answers, but only one of the three is scored. Reason-code agreement is reported
beside the headline rate and **cannot change it**: two reviewers may agree a record is excluded and
disagree about why, and that is a different finding from disagreeing about eligibility.

**Cohen's kappa is descriptive, not a gate.** It is computed and reported, and it is **not** a
verdict threshold — no value of kappa changes ADOPT, EXTEND or RE-SCREEN. Where a rater shows no
variation it is reported as undefined rather than as zero, because expected agreement is then 1 and
kappa is 0/0.

**Incomplete responses cannot be scored.** A single blank or whitespace-only `your_decision`
refuses the entire sheet: no rate, no kappa, no verdict and no report are produced. An exclusion
with no permitted reason code, or a reason code recorded on a non-exclusion, refuses likewise. A
partial sheet therefore yields nothing at all, by design — a rate computed over whichever records
happened to be answered would be a different quantity from the pre-specified one.

### What each verdict means

| Verdict | Agreement | What it means |
|---|---|---|
| **ADOPT** | ≥ 95% | The decisions outside the sample are adopted as recorded and the verification is reported in the methods. It does **not** convert `adopted_from_suggestion` records into `independently_adjudicated` ones — see below |
| **EXTEND** | ≥ 90%, < 95% | **A classification and a workflow pause.** It does **not** authorise or perform an automatic second draw. Nothing in this module draws or scores a second sample. Any extension requires a separately approved sampling frame, second-extension outcome, pooling rule and maximum extension count — all four unresolved (`verification_sample_architecture.md` §7) |
| **RE-SCREEN** | < 90% | The suggestion set is discarded as a decision source and the population **requires** manual human re-screening. This is a **verdict, not a completed action**: reaching it re-screens nothing. The re-screening is human work that must then be done and recorded |

**What an ADOPT verdict does not do.** It does not retroactively make a suggestion-adopted record
an independently adjudicated one. `decision_basis` is a record of which act produced a decision,
and a sample-based agreement figure does not change that act for any record, inside or outside the
sample. D010 and the adjudication requirements above are untouched by any verdict.

### Who is being compared with whom

Four roles are distinct, and conflating them would misdescribe what this exercise measures:

| Role | Who or what | Recorded where |
|---|---|---|
| Automated suggestion producer | tooling, operating on the titles and abstracts | `ta_suggestions_2026-11-01.csv`; the repository names no person |
| Human reviewer | the named reviewer | the `reviewer` column |
| Recorded worksheet decision | the adopted value | `decision`, with `decision_basis` |
| Blinded verification decision | the reviewer's judgement made without sight of the above | `your_decision` in the sample sheet |

Because all 194 recorded decisions are byte-identical to the suggestions, the agreement measures
**one human reviewer's blinded decisions against an automated suggestion set**. It is **not**
inter-reviewer agreement and **not** independent duplicate screening. A discrepancy establishes
that the two differ, not that either is correct.

### Which worksheet the seed came from

The seed is derived from the data rather than chosen, so it is tied to a specific state of the
worksheet. The sample was drawn **before** the M1 migration added `suggestion`,
`suggestion_reason_code`, `decision_basis` and `adjudicated_date`, so the digest that produced it is
the digest of the pre-migration file:

| | |
|---|---|
| Worksheet at the draw | `data/screening/screening_ta.csv` as committed at `c704582` (16 columns, 194 rows) |
| SHA-256 | `5938922a529a7f7318824f4216b4b9ab05b920a14def7c15e72c15ea2a6076eb` |
| Seed | `1496879658` (= `0x5938922a`) |
| Reproduces the committed sample | **yes** — the same 40 reports, in the same order |

That digest is recovered from the preserved commit itself, which is the authoritative record; it is
not reconstructed from the seed, and the seed alone could not determine it.

**Hashing the current worksheet does not reproduce the sample.** The migrated file has a different
digest, `a68623477f81fb14c4b70ada70a5a9775cc8671e4b945152404bdb0c9794fe22`, which yields seed
`2793808711` and selects a different set of 40 records. Anyone auditing the draw must hash the
pre-migration worksheet recorded above, not the file as it now stands. Adding columns changed the
bytes without changing a single decision, which is exactly why the digest used for the draw has to
be recorded rather than re-derived.

A practical caution: the historical digest covers the file's **bytes**, line endings included. The
recorded value is that of the worksheet as it existed on disk, with CRLF endings. Hashing the LF
blob that Git stores for `c704582` gives `9ce12867…` (seed 2632001639), which never drew this
sample. That platform dependence is the reason D020 replaced the rule for later draws.

**The original draw date is UNVERIFIED.** No run log was captured and the sheet has no date column.
The draw necessarily preceded commit `c704582` (2026-11-01 17:48 +0530), but a commit date is not
evidence of when a draw was run, so it is recorded as an upper bound only and never as the date.

### The canonical sampling-frame digest (D020)

Adopted 2026-11-10, **for draws made after that date**. The existing sample is not redrawn and its
seed is not re-derived; see *Which worksheet the seed came from* above for its own provenance.

The earlier rule hashed the worksheet file's bytes, so the seed depended on line endings and
changed when columns were added that the draw never reads. The canonical rule hashes the
**sampling frame** instead — the thing the draw procedure actually consumes.

| | Historical | Canonical (D020) |
|---|---|---|
| Rule name | `file_bytes_crlf_v1` | `ordered_report_ids_v1` |
| Hashes | the worksheet file's bytes | the ordered sampling frame |
| Governs | the existing 40-record sample | every later draw |
| Line-ending dependent | **yes** | no |
| Changes when a later column is added | **yes** | no |

**The specification, reproducible by hand:**

1. **Fields included** — `report_id`, and nothing else.
2. **Record order** — worksheet file order, preserved, never sorted.
3. **Encoding** — UTF-8.
4. **Unicode normalisation** — NFC, applied to each identifier.
5. **Null / empty values** — refused. An empty or whitespace-only `report_id` raises; it is never
   hashed as `""`, because a unit with no identifier cannot be identified.
6. **Serialisation** — the rule version, then LF, then each identifier followed by LF. The version
   is inside the hashed payload, so two rules cannot give the same digest for one frame.
7. **Separator** — LF (`0x0A`) only, whatever the file on disk uses.
8. **Hash** — SHA-256, lowercase hexadecimal, 64 characters.
9. **Sampling frame** — every row of `data/screening/screening_ta.csv`, in file order. No
   filtering, no subsetting, no deduplication.
10. **Versioning** — the rule label is recorded beside every digest; a change of rule needs a new
    version string and a new decision entry.

So the hashed bytes are exactly, with every separator an LF and a trailing LF at the end:

```
ordered_report_ids_v1\nR0001\nR0002\n...R0194\n
```

laid out one line per record, that is:

```
ordered_report_ids_v1
R0001
R0002
...
R0194
```

with no CR anywhere, and no trailing blank line beyond the final LF.

**Why `report_id` alone faithfully identifies the frame.** The draw is positional —
`random.Random(seed).sample(range(len(rows)), size)`, returning the rows at the chosen positions.
It therefore consumes only the *number* of sampling units and *which unit occupies each position*.
`report_id` is the screening unit of analysis (D004) and is unique across the worksheet, so the
ordered sequence of `report_id` values fixes both exactly. Including more columns would make the
digest change when a title typo or an abstract re-import is corrected — events that alter no
sampling unit and no position — and would then report an unchanged frame as a different one. The
chosen field set is sensitive to what the draw depends on, and to nothing else.

**Verified properties** (`tests/test_draw_provenance.py`, 20 tests):

| Invariant to | Sensitive to |
|---|---|
| CRLF versus LF presentation | sampling-frame row reorder |
| the 16-column → 20-column schema change | a frame row added |
| later, irrelevant columns | a frame row removed |
| corrections to non-identifying fields | a `report_id` changed |
| | a change of rule version |

The frame digest of the current worksheet is
`37cc07e64054ef938229fbecec5f7da70f4c9ae419aae9f79b04d642574209ad`, identical to that of the
pre-migration worksheet because the frame did not change. Its first 8 hex digits give seed
`936118246` — which is **not** the historical seed, and is not used to re-derive it.

**Current state: 0 of the 120 response cells are completed.** The sheet is drawn and unanswered, so
**no agreement rate, no Cohen's kappa and no acceptance outcome exist yet.** Scoring it is a
precondition for interpreting the recorded decisions, and nothing in this repository reports an
agreement figure.

The module never writes to `screening_ta.csv` and never changes a recorded decision. Once drawn,
`verification_sample.csv` is protected: it is not regenerated, re-drawn or edited, because redrawing
after seeing the records would destroy the blinding. Filling it in is the reviewer's work and cannot
be generated.

## Unresolved protocol decisions this module does not settle

The provenance rules described above — the two decision bases, the suggested reason code, the
full-text basis and the formal-versus-provisional PRISMA split — are recorded as **D016, D017, D018
and D019, all with status `Proposed — awaiting the reviewer's adoption`**. They are implemented and
enforced in code, but they are **not adopted protocol**. Decisions recorded under them do not count
as protocol-conformant until the reviewer adopts them.

Beyond those, two things are **configurable and explicitly unresolved**, not quietly decided:

1. **Stage assignment of exclusion reasons is a proposal, not protocol.** The table in
   `docs/protocol/eligibility_criteria.md` fixes the reason codes but assigns no stages. The
   `stages` values in `config/screening.yaml` restrict `no_reference_group`, `no_usable_data`,
   `outcome_not_separable` and `duplicate_publication` to full text, on the grounds that they
   cannot be judged from an abstract without guessing. **This needs the reviewer's endorsement**
   before decisions made under it count as protocol-conformant.
2. **No anatomical or histological reason codes exist yet.** The subsite and histology audits
   proposed `wrong_subsite_oropharynx`, `wrong_subsite_lip`, `subsite_not_separable` and
   `non_scc_histology`. None is implemented, because the decisions behind them are open — lip
   scope, the soft-palate/uvula convention, the straddling codes C02.8/C02.9/C05.8/C05.9/C06.80,
   site purity, and whether SCC variants count as SCC. Until they are settled a screener records
   `unresolved`, or `other` with a written justification.

**D025** settles the reference-group question — both types are eligible, never-smoker is the
primary analysis — and applies at *full text*, because `no_reference_group` is unavailable at
title/abstract. **D026** fixes the contrast and affects extraction rather than title/abstract
eligibility. Still open and relevant: **P006** (protocol registration, which should precede
screening) — the title/abstract pass was performed without it, which is a deviation to report.
